# ДЗ4. Противодавление в FastStream и RabbitMQ

В этой работе мы собрали конвейер для обработки цен Brent. Источник
отправляет задачи в RabbitMQ, воркер получает их и запускает inference
модели из MLflow, а результаты сохраняются в PostgreSQL. Главная цель -
проверить, что при медленной обработке очередь не растёт бесконечно, а
источник реагирует на перегрузку.

## Как устроен проект

-   **app.source** - отдельный процесс, который читает CSV и отправляет
    задачи. В памяти остаются последние 11 свечей и текущая задача. Если
    RabbitMQ отклоняет публикацию, источник повторяет отправку с
    увеличивающейся задержкой.
-   **app.api** - HTTP API. Эндпоинт POST /api/v1/tasks публикует задачу
    в RabbitMQ. Если брокер отклоняет публикацию, запись PENDING
    удаляется, а клиент получает 503 и заголовок Retry-After.
-   **app.topology** - создаёт exchange, основную очередь и DLQ.
-   **app.worker** - FastStream-воркер. Он загружает модель из MLflow по
    alias champion один раз при старте. Значение INFERENCE_DELAY_SECONDS
    задаёт задержку обработки. Синхронный вызов model.predict вынесен в
    поток через asyncio.to_thread.
-   **app.database** - хранит статусы задач и результаты в PostgreSQL.
    task_id является первичным ключом, повторная обработка не должна
    создавать второй результат.
-   **app.experiment** - запускает три варианта нагрузки и сохраняет
    измерения в CSV. После запуска таблица результатов в этом README
    обновляется автоматически.

## Что нужно для запуска

Нужны Docker Desktop с Docker Compose, Python 3.11 и доступ к Docker
Hub. Также должна быть запущена часть ДЗ3 с MLflow и зарегистрированной
моделью BrentDirectionModel.

Для локального запуска можно использовать настройки из .env.example. Для
другого окружения значения из этого файла нужно проверить и при
необходимости заменить.

## Противодавление между брокером и воркером

У воркера задан prefetch_count=1. Один процесс обрабатывает одну задачу
за раз, поэтому ему нет смысла забирать сообщения в локальный буфер
заранее. Если запустить две реплики, они смогут обрабатывать по одной
задаче одновременно.

Задержка задаётся через INFERENCE_DELAY_SECONDS. Ожидание сделано через
asyncio.sleep, а model.predict выполняется через asyncio.to_thread.
Поэтому вычисление не блокирует event loop и health-check /healthz может
отвечать во время inference.

## Противодавление между воркером и источником

Для ограничения очереди используется x-overflow=reject-publish и
publisher confirms. Когда очередь заполнена, RabbitMQ отклоняет
публикацию, а источник воспринимает это как сигнал перегрузки и
повторяет отправку той же задачи. Между попытками задержка увеличивается
от 50 мс до 1 секунды. Фиксированной частоты генерации нет, отдельный
неограниченный буфер в источнике не создаётся.

Это удобнее, чем постоянно опрашивать Management API: источник получает
ответ от брокера на конкретную публикацию, а не пытается угадать
состояние очереди по периодическому запросу. Management API здесь нужен
для наблюдения и сбора метрик.

Для проверки запусти источник с ограниченной очередью из папки
mlflow_hw4:

``` powershell
docker compose -f docker-compose.yml -f docker-compose.bounded.yml --profile source run --rm source python -m app.source --count 180 --batch-id demo
```

В конце источник выведет JSON с количеством отправленных и принятых
задач, повторами, отказами публикации и скоростью. В Management UI можно
открыть очередь tasks.bounded и посмотреть, как меняется Ready.

В эксперименте для RabbitMQ 4.3 используется x-max-length=11, а целевое
значение Ready - 12. Это связано с тем, что при reject-publish сообщение
уже может быть в полёте, когда издатель получает отказ. В наших
измерениях максимум Ready в ограниченных сценариях составил 12. При
нескольких параллельных издателях превышение может быть больше.

Чтобы сравнить работу с двумя воркерами, можно запустить
экспериментальный набор compose-файлов:

``` powershell
docker compose -f docker-compose.yml -f docker-compose.bounded.yml -f docker-compose.scaled.yml up -d --scale worker=2 worker
```

prefetch_count остаётся равным 1, поэтому у каждого воркера одна
активная задача. Если нужно изменить лимит очереди, нельзя просто
объявить существующую очередь с другим x-max-length. Нужно остановить
использующие её сервисы и пересоздать пустую очередь либо задать другое
имя очереди. Перед удалением проверь, что в ней нет сообщений.

## Что происходит при перегрузке API

Внешний клиент мы замедлить не можем. Если RabbitMQ отклоняет
публикацию, API удаляет созданную запись PENDING и возвращает 503
Service Unavailable с Retry-After. Заголовок не меньше одной секунды,
его значение рассчитывается с учётом настроенной задержки обработки.

Это load shedding, а не backpressure: запрос уже пришёл в API, и API его
отклоняет, а не регулирует скорость отправки клиента.

## Обработка ошибок и надёжность

-   Используется ручной ack: сообщение подтверждается только после
    сохранения результата в PostgreSQL. Если воркер упадёт до commit,
    RabbitMQ сможет доставить сообщение повторно.
-   Для quorum queue задан x-delivery-limit=3 и настроен dead-letter
    exchange. При ошибке обработчик использует reject(requeue=True), а
    не nack(requeue=True). В RabbitMQ 4.3 reject учитывается в
    delivery-count, а nack с повторной доставкой не увеличивает этот
    счётчик.
-   Когда попытки заканчиваются, задача получает статус FAILED, а
    сообщение уходит в tasks.bounded.dlq. DLQ не очищается
    автоматическим потребителем, поэтому сообщение можно посмотреть в
    Management UI.
-   Некорректные сообщения и конфликт task_id сразу направляются в DLQ.
    Если PostgreSQL недоступен при записи финального статуса, сообщение
    остаётся в DLQ, но статус в базе нужно будет сверить отдельно.
-   task_id имеет уникальное ограничение в PostgreSQL. При повторной
    доставке проверяется hash входных данных, а уже готовый результат не
    перезаписывается.
-   При штатной остановке вызывается broker.stop(). Для завершения
    текущей обработки задано время ожидания, а Docker даёт контейнеру
    время на остановку.

Ручной ack выбран, чтобы не потерять сообщение, если воркер упадёт между
получением задачи и записью результата. Повторы ограничены на уровне
обработки, а x-delivery-limit дополнительно защищает от бесконечных
циклов после сбоев процесса или соединения.

## Коротко по теории

1.  **Команда и событие.** Команда просит выполнить действие и обычно
    адресована конкретному сервису. Событие сообщает о том, что уже
    произошло. Event-driven подход полезен, когда обработка асинхронная
    и у события может быть несколько независимых потребителей. Для
    простого синхронного вызова он может быть лишним.
2.  **Зачем нужен брокер.** Он разделяет producer и consumer по времени
    и скорости, помогает пережить кратковременную перегрузку и
    поддерживает повторную доставку. Взамен появляются дополнительная
    инфраструктура, eventual consistency и необходимость учитывать
    дубликаты.
3.  **Маршрутизация.** В RabbitMQ exchange направляет сообщения в
    очереди через binding и routing key. После ack сообщение удаляется
    из очереди. Kafka хранит записи в логе и позволяет читать их
    повторно по offset.
4.  **Как не потерять сообщение.** Нужны durable очереди, persistent
    сообщения, publisher confirms, ручной ack после commit результата и
    репликация брокера. Также нужно обрабатывать ситуации, когда
    издатель не знает, принял ли брокер сообщение.
5.  **Ack, nack и reject.** Ack подтверждает успешную обработку. Nack и
    reject отклоняют сообщение; в зависимости от параметров оно может
    быть доставлено повторно или отправлено в DLQ. Ack нужно отправлять
    после надёжной записи результата.
6.  **Гарантии доставки.** At-most-once допускает потерю, at-least-once
    допускает повторную доставку. Exactly-once между независимыми
    брокером и БД обычно не получается без общей транзакции, поэтому на
    практике используют идемпотентность и дедупликацию.
7.  **Идемпотентный потребитель.** Повторная доставка одной задачи не
    должна создавать второй результат. В этом проекте для этого
    используется уникальный task_id и проверка hash входных данных.
8.  **Dual write, outbox и inbox.** При dual write запись в БД и
    публикация сообщения могут разойтись при сбое. Outbox сохраняет
    событие в той же транзакции, что и данные. Inbox помогает не
    обрабатывать один message_id повторно.
9.  **Polling, CDC и LISTEN/NOTIFY.** Polling проще, но создаёт
    дополнительную нагрузку и задержку. CDC читает журнал транзакций, но
    сложнее в настройке. LISTEN/NOTIFY не заменяет outbox, потому что
    уведомление не является надёжным хранилищем событий.
10. **Ошибки обработки.** Временные ошибки повторяют с задержкой и
    ограничением числа попыток. Постоянно ошибочные сообщения после
    лимита отправляют в DLQ, чтобы они не крутились бесконечно.
11. **Backpressure, load shedding и rate limiting.** Backpressure
    заставляет источник замедлиться из-за сигнала от потребителя или
    брокера. Load shedding отклоняет часть запросов при перегрузке. Rate
    limiting ограничивает частоту независимо от текущей скорости
    обработки.
12. **Порядок сообщений.** С одним последовательным consumer порядок
    сохранить проще. Несколько воркеров и повторные доставки могут
    изменить порядок завершения, поэтому обычно гарантируют порядок
    только в пределах конкретного ключа или partition.
